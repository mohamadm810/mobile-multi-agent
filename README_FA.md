# Mobile Multi-Agent — راهنمای راه‌اندازی با گوشی

این سامانه یک تیم برنامه‌ریزی چندایجنتی است که روی GitHub Actions اجرا می‌شود؛
برای اجرای چرخه نیازی به روشن بودن کامپیوتر شخصی نیست.

## قابلیت‌های نسخه اول
- هشت نقش ثابت: تحلیلگر نیازمندی، معمار، برنامه‌ریز توسعه، تستر، بازبین مستقل،
  مدیر مرکزی، مستندساز و مدیر استخدام و ارزیابی ایجنت‌ها.
- اتصال Gemini از طریق GitHub Actions Secret.
- حافظه و گزارش در `workspace/STATE.json` و `workspace/REPORT.md` با جایگزینی اتمیک فایل‌ها.
- ثبت خودکار inventory تست‌ها و تفکیک مدل‌های تلاش‌شده از مدل‌های پاسخ‌گوی موفق.
- اجرای دستی از گوشی و اجرای خودکار پس از تغییر درخواست.
- تست‌های خودکار بدون نیاز به کلید API.

## محدودیت هزینه
کد این پروژه رایگان و متن‌باز است؛ اما Gemini API و GitHub Actions سهمیه و محدودیت دارند.
رایگان/نامحدود بودن دائمی هیچ‌کدام تضمین نمی‌شود. مصرف این نسخه با هفت فراخوانی موفق مدل در هر چرخه انجام می‌شود؛ در صورت خطا، تلاش‌های مجدد و مدل جایگزین ممکن است تعداد درخواست‌ها را افزایش دهند. مدل اصلی و جایگزین در فایل گردش کار تنظیم شده‌اند.

## نصب از گوشی اندروید
1. فایل ZIP را استخراج کنید.
2. در GitHub مخزن `mohamadm810/mobile-multi-agent` را باز کنید.
3. همه محتویات پوشه `mobile_multi_agent` را در ریشه مخزن بارگذاری کنید
   (Add file → Upload files). اگر فایل‌های قبلی وجود دارند، قبل از جایگزینی diff را بررسی کنید.
4. در Settings → Secrets and variables → Actions → Secrets، مقدار
   `GEMINI_API_KEY` را به‌عنوان Repository Secret اضافه کنید.
5. مدل اصلی گردش کار `gemini-3.5-flash-lite` است تا اجرای رایگان و کم‌هزینه اولویت داشته باشد؛ در صورت خطای ظرفیت یا محدودیت موقت، مدل جایگزین `gemini-3.8-flash` امتحان می‌شود. نیازی به ساخت متغیر `GEMINI_MODEL` نیست. اگر متغیر قدیمی ساخته‌اید، آن را حذف کنید تا تنظیم گردش کار اعمال شود.
6. در Actions گردش کار `Run Multi-Agent` را باز کنید و Run workflow را بزنید.

## شروع سریع یک پروژه جدید
1. فایل `workspace/REQUEST_TEMPLATE.md` را باز کنید و متن آن را کپی کنید.
2. متن را با اطلاعات پروژه خودتان جایگزین کنید و در `workspace/REQUEST.md` قرار دهید.
3. تغییر را در GitHub commit کنید؛ با ثبت تغییر `REQUEST.md`، چرخه تیم به‌صورت خودکار شروع می‌شود. اگر نمی‌خواهید با هر ویرایش اجرا آغاز شود، متن را ابتدا بیرون از این فایل آماده کنید و فقط نسخه نهایی را یک‌بار جایگزین و commit کنید.
4. در **Actions → Run Multi-Agent** وضعیت اجرای Preflight و سپس مراحل ایجنت‌ها را ببینید.
5. خروجی اصلی در `workspace/REPORT.md` و وضعیت/مرحله بعد در `workspace/STATE.json` قرار می‌گیرد.

**نکته مهم درباره قابلیت فعلی:** تیم فعلی یک تیم تحلیل و برنامه‌ریزی هشت‌نقشی است؛ هنوز مجری خودکار پروژه‌های بیرونی یا عامل deploy نیست. خروجی آن برنامه، تحلیل، ریسک‌ها و پیشنهادهای قابل بازبینی است. برای تبدیل آن به تیمی که تغییرات محدود کد را نیز انجام دهد، مرحله اجرای sandbox و تأیید یک‌باره هر تغییر باید جداگانه تکمیل و آزمون شود.

## کنترل آمادگی پیش از شروع هر پروژه (Preflight)
پیش از هر چرخه، یک کنترل محلی و بدون فراخوانی مدل اجرا می‌شود. این کنترل:
- معتبر بودن و غیرخالی بودن `workspace/REQUEST.md` و رعایت سقف اندازه درخواست؛
- وجود فایل‌های ضروری برنامه و گردش‌کار؛
- پیکربندی حداقل یک ارائه‌دهنده مدل؛
- اعتبار HTTPS و تنظیمات endpoint ارائه‌دهنده OpenAI-compatible، اگر کلید آن تعریف شده باشد؛
- امکان نوشتن امن در پوشه `workspace`؛
- سازگاری نسخه Python را بررسی می‌کند.

اگر هر کنترل ضروری شکست بخورد، اجرای ایجنت‌ها قبل از مصرف API متوقف می‌شود و نام کنترل ناموفق در خروجی workflow نمایش داده می‌شود. مقدار هیچ کلید یا Secret در گزارش Preflight چاپ نمی‌شود. داشتن فقط Gemini یا فقط OpenAI-compatible برای شروع کافی است؛ اما برای افزونگی واقعی باید هر دو Secret جداگانه پیکربندی شوند.

اجرای دستی همین کنترل در محیط توسعه:
```bash
python -m agent.preflight
```

## استفاده روزمره با گوشی
1. مخزن را در برنامه GitHub Mobile باز کنید و وارد بخش **Actions** شوید.
2. گردش کار **Run Multi-Agent** را انتخاب کنید و از صفحه همان گردش کار، **Run workflow** را بزنید.
3. اجرای جدید را باز کنید تا وضعیت Job، مراحل اجرا و Logs را ببینید.
4. برای دیدن خروجی نهایی، به صفحه اصلی مخزن برگردید و از فایل‌های `workspace/REPORT.md` و `workspace/STATE.json` استفاده کنید.
5. متن درخواست بعدی را در `workspace/REQUEST.md` ویرایش و commit کنید؛ این تغییر به‌صورت خودکار چرخه جدید را اجرا می‌کند.

برای اجرای دستی، حساب GitHub باید دسترسی نوشتن به مخزن داشته باشد. اگر دکمه اجرای دستی در نسخه برنامه یا مرورگر موبایل نمایش داده نشد یا عمل نکرد، همان مخزن را در مرورگر با حالت Desktop site باز کنید و از مسیر Actions → Run Multi-Agent → Run workflow اجرا کنید.

- تصمیم‌های تأییدشده را به درخواست بعدی منتقل کنید.

## امنیت و مرز اختیارات
- کلید API فقط در Secret نگهداری شود؛ هرگز آن را در فایل‌ها، Issue یا گزارش وارد نکنید.
- نسخه اول فقط تحلیل و برنامه‌ریزی می‌کند. هیچ shell دلخواه، تغییر مخزن پروژه‌های دیگر،
  حذف فایل، انتشار یا deploy در اختیار مدل نیست.
- خروجی ایجنت‌ها پیشنهاد است و باید توسط انسان بازبینی شود.
- داده مشتری، اطلاعات شخصی و اسناد محرمانه را وارد درخواست نکنید.

## پایداری اتصال API
برای خطاهای موقت HTTP 429/500/502/503/504 و خطاهای موقت شبکه/timeout، هر مدل حداکثر سه بار با تأخیر افزایشی تلاش می‌شود. پس از اتمام تلاش‌ها، در خطاهای قابل‌بازیابی مدل جایگزین امتحان می‌شود؛ خطاهای دسترسی/درخواست مانند 400/403/404 بی‌درنگ گزارش می‌شوند. گزارش، مدل‌های تلاش‌شده را جدا از مدل‌هایی که پاسخ موفق داده‌اند ثبت می‌کند. وضعیت مدل در هر چرخه از نو تنظیم می‌شود تا داده اجرای قبلی وارد گزارش بعدی نشود. اگر ثبت گزارش در شاخه `main` پس از سه تلاش ناموفق بماند، فایل‌های گزارش و وضعیت به‌عنوان Artifact در GitHub Actions برای ۱۴ روز نگهداری می‌شوند.

## کیفیت گزارش چندایجنتی
هر نقش خروجی کوتاه و اختصاصی تولید می‌کند؛ فقط یافته‌های مرتبط نقش‌های قبلی به مراحل بعد منتقل می‌شود تا از تکرار متن و رشد بی‌رویه گزارش جلوگیری شود. خروجی ایجنت‌ها تحلیل مدل است و جایگزین بازبینی انسانی یا اجرای مستقل تست‌ها نیست. اگر اجرا شکست بخورد، وضعیت `failed` و خلاصه خطا در `workspace/STATE.json` ذخیره می‌شود؛ Workflow نیز این وضعیت را حتی در اجرای ناموفق به مخزن برمی‌گرداند.

## عیب‌یابی
- خطای `Missing GEMINI_API_KEY`: Secret با نام دقیق بالا تعریف نشده است.
- خطای HTTP 400/403/404: مدل انتخابی یا دسترسی API را در Google AI Studio بررسی کنید.
- خطای 429: محدودیت نرخ/سهمیه؛ بعداً دوباره اجرا کنید یا مدل/سهمیه حساب را بررسی کنید.
- اجرای ناموفق: Actions → اجرای مربوط → Job → Logs.
- اجرای تست‌ها بدون API: در Actions گردش کار `Tests` را اجرا کنید.

## مدیریت منابع انسانی ایجنت‌ها
- نقش هشتم پس از بررسی خروجی‌ها، عملکرد نقش‌ها و میزان هم‌پوشانی را ارزیابی می‌کند.
- می‌تواند ایجنت سفارشی استخدام کند، هر نقش غیرمدیر را با حفظ سابقه به‌طور برگشت‌پذیر غیرفعال/بازیابی کند و دستورالعمل نقش‌های غیرمدیر را اصلاح کند؛ تغییرات از چرخه بعد اعمال می‌شوند.
- حداکثر ۵ ایجنت سفارشی فعال و حداکثر ۲ تغییر منابع انسانی در هر اجرا مجاز است.
- مدیر مرکزی و خود مدیر منابع انسانی محافظت شده‌اند. هرگونه پیشنهاد عزل یا جایگزینی مدیر مرکزی فقط برای تأیید انسانی گزارش می‌شود.
- استخدام خودکار فقط در صورت درخواست صریح کاربر یا وجود شکاف تکرارشونده و مستند مجاز است؛ هدف افزایش دقت و سرعت با کنترل هزینه است.

## توسعه نقش‌ها
برای افزودن نقش پایه جدید، prompt آن را در `agent/roles.py` تعریف و مرحله آن را در
`agent/run.py` ثبت کنید. نقش‌های تخصصی سفارشی از طریق مدیر استخدام در `workspace/TEAM.json` نگهداری می‌شوند. نقش جدید باید فقط خروجی متنی/تحلیلی تولید کند؛ افزودن ابزار اجرایی
نیازمند طراحی مجوز و تأیید انسانی جداگانه است.
